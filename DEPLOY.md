# Деплой в git — правила

> ## 🔴 Правило №1: пуш только по явному разрешению
>
> Не коммитить и не пушить каждую мелкую правку. Сначала накопить изменения
> локально, проверить их вместе — и выложить одним разом.
>
> Разрешение на прошлый пуш **не** переносится на следующий. Нужно явное
> «пуш», «залей», «коммить» или аналогичная команда.

> ## 🎯 Правило №2: один батч — один осмысленный коммит
>
> В батч входят все изменения, которые пользователь успел попросить с момента
> прошлого пуша. Не оставлять «полузалитые» логические куски.

## Порядок работы

1. Делать правки **локально**.
2. Проверить локально:
   - `npm.cmd run typecheck`;
   - `npm.cmd test`;
   - `npm.cmd run build`;
   - если менялся пользовательский функционал — `npm.cmd run dist`.
3. Показать, что изменилось: список файлов, суть, результаты проверок.
4. **Ждать явного разрешения на пуш.**
5. После разрешения:
   - `git status`;
   - один коммит на весь батч;
   - `git push origin main`;
   - проверить, что remote указывает на новый коммит.

## Git-ограничения

- Работаем в `main`; отдельные ветки — только по договорённости.
- ❌ force-push и переписывание истории без отдельного разрешения.
- ❌ коммит `release/`, exe и прочих сгенерированных артефактов.
- ❌ секреты, токены, ключи, локальные настройки.
- ✅ осмысленное сообщение коммита: что и зачем изменено.
- ✅ перед пушем проверить `git status` и diff на случай мусора.

## GitHub Release

- Публикация release/exe — отдельное действие и **только по явному разрешению**.
- Перед release: собрать exe, посчитать SHA256, проверить запуск.
- Не обновлять существующий release без разрешения.

## Разрешение

Разрешение действует **только на тот набор изменений**, о котором шла речь.
После него новые правки снова ждут разрешения.

Если сомневаюсь — **спрашиваю**, а не пушу.
